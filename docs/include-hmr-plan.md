# Include 与 HMR 实施计划

> 状态：Proposed<br>
> 类型：Specification<br>
> 适用范围：`@nya/include`、`@nya/hmr` 与 Loader 公开扩展<br>
> 实施环境：现有 Node.js ESM 宿主，优先验证 Windows 与 Linux

本文保留补齐配置文件和热更新能力的阶段与验收条件。2026-09-05 已开始落地代码，当前证据记录在文末；本文仍是 Proposed 计划，实际支持范围以[核心概念](./concepts.md)、源码和测试为准。

已有[通用配置与持久化计划](./config-persistence-plan.md)继续负责单文件 JSON 闭环的详细规范，[ADR-0014](./adr/0014-config-persistence-boundary.md)继续表达配置与运行状态的边界。本文在其上安排 YAML、多文件配置、监听和真正的模块热替换；HMR 的跨模块选择另见 [ADR-0015](./adr/0015-module-generations-and-replacement.md)。

## 要交付的使用体验

1. 在 JSON 或 YAML 中声明组件、配置、分组和禁用状态，启动应用即可恢复。
2. 通过配置控制器修改配置、启停或移除组件，修改保存回所属文件，下一次启动仍生效。
3. 一个配置文件可以挂载另一个配置文件，并能指出每个条目的来源。
4. 开启配置监听后，保存文件会更新运行中的组件；无效文件不会把正在运行的应用清空。
5. 开启代码 HMR 后，修改受支持的本地组件或其本地依赖，在同一进程内清理旧运行并安装新定义。没有共享代码或服务依赖关系的分支继续运行。

前三项属于 Include，第四项由 HMR 的配置监听模式触发 Include，第五项属于 HMR 的代码替换模式。配置刷新、组件重新运行和进程重启分别报告，不能使用同一个“热更新成功”概括。

## 模块分工与默认范围

| 模块 | 拟承担的职责 | 资源所有者 |
| --- | --- | --- |
| `@nya/include` | 文档协议、JSON/YAML 解析、来源归属、变更预览、保存、手动刷新和 Loader 协调 | 控制器拥有文档状态、写入队列及挂载资源 |
| `@nya/hmr` | 可选文件监听、事件合并、代码构建、模块依赖图、版本产物、替换调度和报告 | HMR 安装实例拥有 watcher、构建任务和产物租约 |
| `@nya/loader` | 继续管理内存树；新增与文件无关的公开定义替换协议和目标版本检查 | Loader 拥有 Entry 与其安装，复用现有串行队列 |
| `@nya/core` | 继续负责配置 Schema、依赖变化、启动和清理 | Core Fiber/Effect |
| 宿主 | 显式启用组件、指定文件与源码范围、显示结果、处理退出期限和重启请求 | 宿主进程；库不会自行退出借用的宿主 |

Include 的首个可运行交付仍为单文件 JSON；完整 Include 阶段补上 YAML 和多文件挂载。文件监听仅在显式安装 HMR 或启用对应适配模式后开始，导入包没有监听和写文件副作用。

HMR 首轮支持显式登记的本地 JS/TS 组件及可静态确定的本地模块依赖。TS 使用受控构建输出；常规 Loader 的生产加载规则不变。浏览器 HMR、运行中改写 Core、原生扩展替换、任意动态模块路径和自动迁移组件局部变量不属于首轮支持范围。遇到不支持的模块图或宿主依赖变化，报告需要进程重启，由宿主决定如何处理。

## 实施顺序

每个阶段形成一个或多个可评审 PR。P0 为必要能力或前置验证，P1 为其后的完整功能；不能只完成 P0 就宣称 Include/HMR 全部完成。

| 阶段 | 优先级 | 交付内容 | 完成条件 |
| --- | --- | --- | --- |
| 0. 固定边界并验证 HMR 路线 | P0 | 固定文档协议、所有权和替换报告；做最小模块版本原型，比较构建产物的依赖身份和路径行为 | 原型覆盖共享模块、传递依赖、循环导入、单份 Core、源文件资源路径；失败项有明确支持边界，不依靠 Node 私有缓存接口通过 |
| 1. Include JSON 闭环 | P0 | 按既有持久化计划阶段 1—4 落地版本化文档、纯预览、保存并应用、关闭及重启恢复 | 仓库外实际 tarball 完成加载→编辑→保存→关闭→恢复；保存结果与运行结果分开 |
| 2. YAML 与多文件挂载 | P1 | YAML 文档适配、来源位置、挂载命名空间、逐文件写回、循环及重复来源检查 | JSON/YAML 表达相同声明；编辑写回来源文件；错误定位到文件和字段；跨文件关系不造成误删除 |
| 3. 配置文件监听 | P1 | `@nya/hmr` 的配置监听模式；调用 Include 的既有刷新入口 | 原子保存、重复事件、删除恢复、自身回写、无效内容和关闭竞态全部通过；无需启用代码构建 |
| 4. Loader 公开定义替换 | P0 | 显式替换已解析的 Component，检查目标版本，在同一队列处理缓存和安装 | 稳定 Entry ID；同模块多实例一致；禁用条目不被启用；清理失败不继续替换；已有 API 行为保持 |
| 5. HMR 模块版本与依赖图 | P0 | 构建适配器、依赖归属、共享模块替换集合、不可变版本产物、宿主外部依赖解析 | 改间接依赖确实使用新代码；共享本地模块不被意外复制；产物路径不引入第二份 Core；旧任务不能发布 |
| 6. 同进程代码热替换与恢复 | P1 | 将 watcher、构建结果、Loader 替换和显式恢复连接起来 | 成功替换期间 PID 不变；旧 Effect 先清理；无关分支不重启；失败分阶段报告；代数上限可请求宿主重启 |
| 7. 综合消费者与发布 | P0 | 专用示例、跨平台真实进程测试、文档、API 基线和候选打包 | 完整操作场景通过 `npm run release:check` 及 Windows/Linux 矩阵，发布支持范围可追溯到测试 |

依赖顺序为：0→1→2→3，0→4→5→6，最终共同进入 7。Include 的单文件版本可以先单独交付；YAML、多文件与完整 HMR 仍保留在本计划的必需后续工作中。

## Include 的实施约束

### 单文件协议与写入

沿用[持久化计划](./config-persistence-plan.md)的全部约束，阶段 0 将其落实为类型/Schema 和测试，不另维护第二套手工 API 参考。至少固定以下事项：

- 文档具有格式版本、有序的声明树和稳定 ID；只保存原始配置与安装声明，不保存 Fiber ID、运行状态、错误或诊断。
- 程序化输入限制为可无损表达的 JSON 数据；依赖声明与调用配置中的 `null` 不混用。省略可选字段能够清除旧覆盖。
- `isolate` 的字符串标签由控制器稳定映射为 Symbol；普通分组移动不改变条目身份。
- 控制器使用自有挂载根，并记录哪些 Entry 来自文档。宿主与动态条目不被整体导出；删除受管祖先的级联影响必须出现在预览中。
- 编辑从 Include 的统一入口提交。直接调用 Loader 或 `fiber.update()` 改变运行时，不自动反向持久化；显式采纳运行时修改需要另有可序列化的声明输入。
- 执行顺序为静态预检、检查来源基线、保存目标、协调运行、报告结果。保存失败不触发本次运行修改；运行失败不抹掉已保存目标，也不自动调用 `resolve()`。
- 卸载控制器时停止新请求，排空或明确终止尚未开始的工作，按所有权清理挂载；借用的 Root 和 Loader 继续由宿主管理。

### YAML 与多文件

YAML 首轮表达与 JSON 相同的数据集合；拒绝重复键、非字符串映射键、自定义执行标签和无法往返的数据。拟采用 `yaml` 的 Document API 处理来源位置和局部编辑，尽量保留未修改节点的注释；不承诺任意 YAML 格式字节级不变。锚点/别名首轮明确拒绝，后续支持需要单独往返测试。[YAML 官方文档](https://eemeli.org/yaml/)提供文档节点、注释和解析选项，具体依赖版本在实施时锁定。

多文件挂载属于配置文档协议，由 Include 编译为现有 Group/Component Entry；不要求给 Loader 增加文件专用 Entry 类型：

1. 根控制器有明确命名空间，挂载有稳定 ID。运行时 ID 由根命名空间、include 挂载链和文件内 ID 编码得到；普通 group 位置不进入身份，避免组内迁移改变 ID。
2. 子文件的相对路径从声明它的文件目录解析；组件默认基址来自所属文件目录，并允许显式覆盖。
3. 全部来源先读取、静态校验和展开，再改变运行树。规范化真实路径后检测包含循环；首轮拒绝同一文件被重复挂载，避免隐含共享写入。
4. 每个声明保存来源文件、文档位置和内容基线。单次持久化编辑只提交一个来源文件；挂载子树的内容写回子文件。
5. 跨文件移动、同一请求同时编辑多个文件首轮明确拒绝。分别编辑多个文件不具有事务保证；从外部同时改文件时读取来源版本集合并重检，变化中则重新读取。
6. 首次启动缺文件或文档非法时，在安装受管树前失败。运行期间文件缺失或非法，保留已接受的整份目标，修复后重新刷新。
7. 解除挂载会清理对应运行树和控制器索引，但不删除用户的配置文件。

### 监听和结果

Include 提供手动刷新、变更预览、编辑保存、读取报告和等待稳定的入口；确切命名从实现类型生成参考。报告包含目标版本、各文件基线/保存结果、实际逐 Entry 状态以及部分执行错误。

HMR 的配置监听模式只把文件事件变为刷新请求。Include 继续拥有保存/应用队列；手动编辑、外部刷新和自身回写使用同一内容基线判断。监听父目录并重新确认目标文件，以覆盖编辑器替换文件的保存方式；内容相同则不重复协调。重复事件合并，未知文件名事件触发重读检查，目录/文件删除不能被解释为空配置。

监听集合随 include 挂载变化更新，先建立新监听再释放旧监听，避免刷新期间漏掉新来源的保存。初次加载失败的来源及其父目录也保留恢复检测，不能只监听上次成功加载的文件。

## HMR 的实施约束

### 模块替换需要新的公开协议

目前 Loader 只在 Resolver 完整请求变化时重新解析成功定义，而 Node ESM 也有独立的 URL 缓存。重复 `import()` 或调用 `resolve()` 不能代替 HMR。[Node 22.12 ESM 文档](https://nodejs.org/download/release/v22.12.0/docs/api/esm.html#urls)说明 URL 身份及缓存规则。

阶段 4 的替换操作暂用工作名 `replace`，确切签名在类型实现中确定。协议必须满足：

- 接收已经解析的新定义及预期的声明版本；文件路径、构建器、watcher 和 Node 模块缓存不进入 Loader。
- 预检 ID、当前 Resolver 请求和目标版本，在清理前发现已过期计划；被删除、移动或改过配置的条目不能被旧构建覆盖。
- 同一次提交处理匹配的全部 Entry，并去掉祖先/后代重叠的重复清理。阶段 0 明确 HMR Resolver 的版本映射与 Loader 定义缓存的共同提交边界，避免后续新建条目又读到旧定义。
- 当前有效版本用于未来的新建、移动、重新启用和失败恢复；Entry 的原始 `name`、配置与稳定 ID 不改成产物文件路径。
- 禁用条目只更新将来安装使用的定义；等待依赖的条目保持真实状态，替换完成不等于全部 ACTIVE。
- 子树内现有 Entry 的声明继续保留，手工安装的子 Fiber 按 Core 所有权清理。动态创建的 Entry 不被自动写入文件或猜测删除；组件重复声明相同 ID 的使用方式必须有示例和测试。
- 保留五种现有 Entry 状态；构建、导入、清理、安装和需要重启等信息进入单独的 HMR 报告。
- `create()` 生命周期重入继续适用；替换操作在会等待自身的生命周期路径中拒绝。

### 构建与版本产物

代码监听限定在宿主登记的源码范围、已知模块依赖和必要的构建配置；排除版本产物、普通构建输出、业务数据、`node_modules` 和 `.git`，避免输出再次触发自身构建。初次构建失败时仍监听源码范围内的创建/删除，以便补齐缺失导入后恢复；成功构建后再更新精确依赖集合。配置文件事件交给 Include 刷新，不重复触发代码替换。

采用“受控构建 + 不可变版本产物 + 原生 ESM 导入”的路线，不操作 Node 私有模块缓存。原计划考虑 esbuild；实际实现直接使用 TypeScript 5.9.3 的 AST、strict 检查与逐模块转换，以保留原生模块边界。未运行 esbuild 对照实验，不把替代方案写成已被实测否定。选择依据和测试见 [ADR-0015](./adr/0015-module-generations-and-replacement.md)。

阶段 0 必须通过原型确定输出组织方式，再进入完整实现：

1. 同一替换集合的共享本地模块只能有一份身份。不能独立打包每个入口而复制共享 Service 类、Symbol 或可变模块状态；多入口输出的循环导入和执行顺序必须实测。
2. 变化集合以受管模块图计算。共享本地模块连接的多个入口作为同一替换集合，变动可能扩展到这些入口；没有关系的集合保持原运行。
3. `@nya/core`、其他共享 Nya 包及首轮不热替换的 npm 依赖保持外部依赖，从原始宿主/导入者位置解析。临时输出目录不能改变包解析结果或产生第二份 Core。
4. 生成带源码/构建选项摘要的不可变产物及 source map。源文件在构建期间再次变化时丢弃已过期候选，整个集合重新构建；不发布来自混合输入的产物。
5. 必须验证 `import.meta.url`、相对资源、字面量动态导入及 package imports。能受控复制或映射的资源纳入产物；未登记的运行时文件路径、不可枚举的动态导入等报告不支持，不能悄悄复用旧依赖。
6. Node 内建模块和外部包保持宿主身份；宿主入口、共享 Nya 包、lockfile、解析规则等变化请求进程重启。其影响不会伪装成局部替换。
7. 运行中的集合和可显式恢复的上一代持有产物租约。清理磁盘文件不等于卸载 Node 已导入模块；累计导入代数及失败候选也计入限制，到上限停止导入并请求宿主重启。

当前实现选用保留模块边界的转换输出。共享身份、循环执行、资源路径与原生消费者测试用于约束该选择；不把某一构建器的能力推定为任意模块语义兼容。

### 替换流程和失败语义

正常流程为：合并变化 → 计算依赖集合 → 构建/类型检查 → 导入候选定义 → 检查最新声明版本 → 清理旧运行 → 提交定义版本 → 安装新运行 → 汇报逐 Entry 状态。

候选导入会执行模块顶层代码，不能称为无副作用预检。支持 HMR 的组件应把连接、监听、后台任务等长期资源放在 Core 管理的启动/Effect 中；对任意顶层副作用不作撤销保证。候选执行挂起时，外围不能强行取消用户 Promise，由宿主期限策略处理。

| 发生位置 | 处理与报告 |
| --- | --- |
| 构建或类型检查失败 | 保留旧运行，报告源位置，等待新的修改或显式重试 |
| 候选导入或导出协议失败 | 保留旧 Fiber；报告已经执行过候选顶层代码，不能保证其外部副作用被撤销 |
| 提交前目标版本已变化 | 丢弃过期计划，重新读取声明；不把删除的 Entry 复活 |
| 旧运行清理失败 | 停止该替换集合，不自动解除 Loader 阻断；已完成的清理按真实状态报告 |
| 新运行配置/启动失败 | 保存目标版本与逐项结果；不宣称完整回滚，不无限自动重试同一候选 |
| 服务暂时缺失 | 报告 PENDING 和依赖诊断，由 Core 按原协议等待 |
| 用户显式回退上一代 | 作为另一次清理和安装执行；可再次失败，不承诺恢复业务内存或外部数据 |
| 版本数量上限或不支持的依赖变化 | 报告需要重启；已有开发宿主可接入退出协议，库不自行结束宿主进程 |

HMR 替换代码不向 Include 文档写入版本产物、失败状态或临时路径。配置编辑与 HMR 可各自准备，最终通过 Loader 队列和预期版本检查避免过期提交；保存已完成但应用被新状态打断时，Include 如实报告并按最新目标重新规划。

### 关闭和所有权

卸载 HMR 时停止接受事件、关闭 watcher、取消防抖任务和构建工作；已经进入用户导入或生命周期的任务必须等待其收尾或交给宿主期限处理。关闭后完成的候选不能再安装组件。已经运行的借用应用由原所有者关闭，当前产物的保留责任必须交接或继续持有至其运行结束。

代码替换默认重新建立组件运行，不保留任意闭包变量。需要保留的业务状态放在独立服务或存储中；跨版本状态迁移协议后续另行设计。

## 验收与交付

### 必须覆盖的场景

| 场景 | 可观察验收结果 |
| --- | --- |
| JSON/YAML 保存后关闭并重启 | 恢复声明、配置、顺序和禁用状态，运行快照未被持久化 |
| 修改子文件、包含循环、重复来源、外部覆盖 | 正确定位来源；错误不改已接受运行；只写目标来源文件 |
| 原子保存、重复事件、自身回写、删除后重建 | 监听持续有效；无循环应用或误清空 |
| 修改组件、间接依赖、共享模块、循环模块 | 使用新代码；同一模块应共享的引用一致；支持矩阵与实际结果一致 |
| 同一定义多个 Entry、祖先与后代同时受影响 | 替换集合一致，旧资源只清理一次；稳定 ID 保持 |
| 禁用、PENDING、动态 Entry、服务消费者 | 不意外启用条目，不误删声明；依赖传播由 Core 完成并可诊断 |
| 配置编辑、移动/删除与构建同时发生 | 旧构建不能覆盖新配置或复活条目；最终结果与目标一致 |
| 构建/导入/清理/启动失败及显式回退 | 逐阶段报告；没有无声部分成功、自动清理解锁或伪称事务回滚 |
| 连续替换与关闭 | 检查活跃 Fiber、Effect、监听器、定时器和构建任务；正常循环无资源累计，缓存代数达到门限时请求重启 |
| 真正的局部热替换 | PID 保持，旧清理先于新启动，无代码共享或服务依赖的分支启动计数不变 |
| 宿主重启降级 | 先确认旧应用退出再启动新的；超时与强制退出如实报告 |
| 特殊路径及宿主包解析 | 中文、空格、`#`、`%`、不同 cwd 及配置目录有效；仅一份 Core |

采用纯规划单测、Loader 生命周期集成测试、临时文件测试和真实子进程消费者测试。时序验收以事件和状态握手为主；watcher 的真实系统行为仍需端到端覆盖，不能全部用 mock 替代。

### 预计变更位置

- `packages/include/src/`：文档类型/Schema、JSON/YAML 适配、来源图、规划器、存储和控制器。
- `packages/hmr/src/`：配置监听、源码图/构建适配、版本管理、替换协调及结果类型。
- `packages/loader/src/`：公开替换协议、目标版本检查、缓存与队列协调；对应测试进入 `packages/loader/tests/`。
- `examples/`：增加 Include/HMR 专用示例，复用现有宿主退出思路；保留 task-journal 原有默认行为。
- `scripts/`、根 `package.json`、`api/` 和 CI：接入新包与独立消费者，扩展当前四包清单和 Linux 单平台检查。
- 包 README、`docs/concepts.md`、兼容政策、迁移说明及设计状态：随实际实现同步，不能在计划阶段提前写成 Current。

实施代码默认运行 `npm run check`；公共声明变更生成并审查 API 基线；候选执行 `npm run release:check` 和真实 tarball 消费者。Include 从阶段 1 起就需具备独立消费者，最终阶段再验证完整组合。

最低 Node 22.12.0 与 Node 24.x 分别验证，Windows 和 Linux 均覆盖文件替换、watcher、进程退出和模块解析。实际锁定的 Node/依赖版本写入测试记录。两个新包沿用当前同批候选交付方式，peer 范围和公开扩展按[兼容政策](./compatibility.md)审查，不由本计划指定虚构的已发布版本。
