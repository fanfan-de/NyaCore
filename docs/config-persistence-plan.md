## 目标与当前基础

首个交付目标是：宿主可以从一个 JSON 文件恢复声明的 Entry 树，通过统一入口保存配置修改，重启后恢复最新目标，并能分别判断保存结果与组件运行结果。

## 范围与分层

配置适配器位于 Core 和 Loader 之外，采用 `@nya/include` 名称，目录为 `packages/include/`。现已加入同批 `0.1.0-rc.1` 本地 tarball 交付，不表示已发布到 npm。

包内分开维护文档解析与验证、变更规划、文件存储、Loader 协调四项职责，首版不提前拆成多个包。Core 继续负责组件生命周期与 Schema；Loader 继续管理内存树；宿主负责文件位置、启动和关闭策略。

首版支持单个 JSON 文档、一个配置控制器和受其管理的 Entry。跨文件 include、数据库存储、任意运行时对象序列化、多进程并发写入、运行时批量事务和模块 HMR 后置。文件监听在手动加载与保存稳定后增加。

## 必须先确定的语义

### 文档与归属

- 文档带格式版本，使用稳定 Entry ID 和显式有序树结构；不持久化 Fiber ID、状态、错误或依赖诊断。未来版本不能由旧实现猜测读取或覆盖。
- `config`、对象形式的 `inject` 和 `intercept` 仅接受明确的 JSON 数据子集。程序化输入中的函数、Symbol、BigInt、循环引用、稀疏数组、非有限数值和需要自定义序列化的对象应报出字段路径，不依赖 `JSON.stringify()` 静默丢失或转换值。
- 保存原始输入；Core Schema 转换结果不反向写入配置。完整文档中省略字段表示默认或清除旧覆盖，显式 `null` 保持为数据；适配器负责映射成 Loader 的字段清除操作。
- 仅声明服务依赖与传入 `null` 调用配置保持不同含义。阶段一定义数组形式和对象形式的支持边界；不能用 `null` 替代无法写入 JSON 的 `undefined`。
- `isolate` 拟使用文档作用域内的字符串标签，由适配器在存活期间稳定映射为 Symbol。映射不跨 Root 隐式共享，也不反向序列化任意已有 Symbol；资源归属和映射释放需覆盖测试。
- 配置基址从来源文件目录建立绝对 `file:` URL；文档中的可选相对覆盖先规范化再交给 Loader，不依赖进程工作目录。
- 控制器显式记录文档管理的 ID。宿主安装的 Entry 和组件动态创建的 Entry 不会因缺席于文件而被导出或删除，也不直接将 `loader.entries()` 保存为文档。
- 删除文档管理的父 Entry 仍会按 Loader 所有权清理全部后代。变更预览必须列出当前树中可确定的结构级联影响，包括动态后代；若保留的声明条目需要迁出，必须先规划迁移，不能先删除父级再发现数据已丢失。

### 验证与运行结果

文档预检只验证格式、JSON 值、ID 冲突、树结构、字段和基址，以及是否存在合法的操作顺序。预览不得调用 Resolver 或安装组件；动态 import 可能执行模块顶层代码，不能当作无副作用的验证。

组件 Schema、服务依赖、启动及清理由现有 Core/Loader 流程处理。预检通过不表示组件配置一定有效或应用已经就绪；若将来要求保存前验证组件 Schema，应另行设计公开验证能力，不复制 Core 私有实现。

适配器只对计划涉及的受管声明执行直接树操作；服务提供者变化仍可能使其他根或兄弟消费者清理、等待或重启。纯预览不能穷尽依赖传播与生命周期副作用，执行报告需记录观察到的真实结果，也不能将结构影响范围当作运行影响范围。

控制器分别报告文档版本、保存是否完成、运行时协调结果及逐 Entry 状态。`pending` 是依赖尚未满足；`failed` 是执行失败；等待稳定不等于就绪。删除返回清理错误时，还需报告 Entry 是否实际已删除，不能根据 Promise 拒绝推断树未变化。

### 保存、冲突与恢复

程序化编辑采用“预检与规划 → 检查读取基线 → 保存目标文档 → 应用到 Loader → 汇报实际状态”。保存失败时不开始这次运行时修改；保存成功但运行失败时保留目标文档，明确报告部分应用，不自动恢复旧配置或调用 `resolve()`。

文件采用同目录临时文件和替换提交，验证正常异常路径中不会留下截断的正式文件。是否承诺断电后的落盘持久性需单独验证，不能从 rename 成功推导。

首版限制单宿主写入，控制器串行处理操作。使用文件内容摘要或等价基线检测已知的外部修改，冲突时拒绝覆盖并要求重新读取；这不承诺消除任意外部写入者与最终文件替换之间的竞态。

已保存的文档是下一次启动的目标，运行快照用于描述实际状态。外部文件无效时保留当前已接受目标和运行状态，报告来源位置，不自动覆盖外部文件。启动时遇到无效文档，应在修改受管树前失败。

运行时协调不是事务。应用前模拟操作顺序，应用中按实际快照更新结果；遇到清理失败或前置条件失效，停止依赖该失败步骤的后续操作并重新规划，保留无关条目。已运行的副作用不承诺撤销；恢复使用显式修正、重新应用或 Loader 的恢复入口。

## 实施阶段与验收

每阶段形成一个可评审的交付单元，具体 PR 可按测试规模拆分。阶段二与阶段三的纯模块可以在阶段一契约稳定后并行实现，集成验收按下列顺序进行。

| 阶段 | 优先级 | 交付内容 | 完成条件 |
| --- | --- | --- | --- |
| 1. 固定文档协议 | P0 | 评审 ADR-0014；确定包名；实现版本化 JSON 类型、解析、验证、归属和标签映射；参考内容从类型或 Schema 生成 | 非法值有字段路径；未知版本拒绝；稳定 ID、顺序、禁用状态、原始配置可往返；基址和隔离映射有测试 |
| 2. 实现内存协调 | P0 | 根据受管目标与当前树生成纯变更预览；执行器只调用 Loader 公开操作；覆盖创建、更新、启停、迁移、排序和删除；记录逐步结果 | 已收敛的相同文档重复应用无额外重启；直接树修改限于受管声明；依赖传播遵守 Core 行为；ID 冲突预检拒绝；保留条目迁出后再删祖先；动态条目归属正确；失败后报告与真实树一致 |
| 3. 完成持久化闭环 | P0 | 文件读取、序列化、临时文件替换、基线冲突检测；统一保存并应用入口；重启恢复与显式恢复 | 保存失败不触发本次运行时修改；已保存但失败的配置可追踪；配置移除字段确实清除旧值；重启恢复顺序及禁用条目；已检测外部变更不被覆盖 |
| 4. 消费者与交付验证 | P0 | 可独立运行的配置树示例；通过实际 tarball 验证新包；更新文档、生成声明基线与打包脚本 | 仓库外完成加载→修改→保存→关闭→重启恢复；声明和运行时只有一份 Core；宿主清理失败与路径用例通过；形成明确支持矩阵 |
| 5. 接入文件监听 | P1 | 可选监听适配器；合并重复事件；内容去重；共用同一验证、规划和执行队列；处理替换、删除和恢复 | 编辑器原子保存仍可继续监听；自身回写不循环；无效内容保留运行态；删除文件不会被解释为空树清空；卸载后无监听或延迟任务残留 |

**最小可交付版本以阶段一至三为功能范围，并通过阶段四的消费者验收。** 届时能够手动加载、持久化修改并在重启后恢复；自动监听不阻塞这次交付。

## 重点验证矩阵

| 场景 | 预期 |
| --- | --- |
| 重复 ID、非法父子结构、与未受管 ID 冲突 | 在修改 Loader 前拒绝；错误指向文档位置 |
| 文档与运行时含动态条目 | 只导出文档声明；动态条目不因对账缺席被删除；祖先删除的级联影响可见 |
| 纯配置修改、字段删除、重复加载 | 使用现有配置生命周期；清除语义正确；无变化不重启 |
| 迁移与删除交织、父子反转 | 模拟可行顺序；无法安全规划的变更在执行前拒绝，不承诺所有组合首版均可执行 |
| 磁盘写入或替换失败、过期保存请求 | 正式文件保持可解析；运行时不进入本次应用；临时资源得到清理；已知冲突明确上报 |
| Schema 拒绝、服务缺失、启动失败 | 保存结果与运行结果分开；逐 Entry 显示真实状态；诊断不写入文档 |
| 提供者变化影响其他根或兄弟消费者 | 保留其他声明归属；允许 Core 执行依赖清理和恢复；报告观察结果，不承诺运行影响仅限结构子树 |
| 清理失败、删除后抛错 | 保留错误和实际树状态；不自动重试旧 disposer，不无限恢复或声称已回滚 |
| 应用中再次提交配置或外部保存 | 串行处理，重新检查基线与实际树；后续结果不被过期任务冒充 |
| 保存后进程退出、重新启动 | 从完整目标文件恢复；不依赖前一次 Fiber ID 或内存快照 |
| 文件被替换、删除、暂时写成无效内容 | 重读并验证；报告异常，保留已接受目标；恢复合法文件后可继续应用 |
| 控制器卸载及初始化失败 | 停止接收新操作，清理自有 watcher、计时器和临时资源；已开始的操作有明确收尾；不关闭宿主借用的 Root/Loader |
| Windows 路径及支持的其他平台 | 空格、中文、`#`、`%` 和相对模块路径按文件基址解析；文件替换行为在支持矩阵中实测 |

## 文档、检查与后续边界

代码实施时默认运行 `npm run check`。新增公开包后同步接入 workspace 的构建、测试、类型检查、声明基线、消费者和打包检查；新包是否纳入同版本发行与 peer 范围需更新兼容政策。交付候选运行 `npm run release:check`，不能仅用包内单测代替仓库外验证。

每完成一项公开能力，同步更新包 README 和 `docs/concepts.md`，并只将已有实现与测试支持的目标条目标记为 Current。本轮仅制定计划，现有实现说明保持原状；文档修改运行 `npm run docs:check`。

后续消费者优先验证通用配置接口；AnyboxV2 的具体接入取决于其宿主需求，不能由本计划宣称兼容已经验证。源码开发重启可继续沿用现有示例思路。跨文件 JSON 配置在单文件归属和冲突处理稳定后扩展；格式范围遵循 [ADR-0016](./adr/0016-json-only-configuration.md)，不再规划 YAML；模块 HMR 单独立项，先确定模块图、缓存失效、替换和失败恢复协议，不以文件监听或 `resolve()` 代称 HMR。
