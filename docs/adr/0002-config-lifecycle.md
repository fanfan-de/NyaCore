# ADR-0002：配置生命周期与 Fiber 串行协调

> 状态：Accepted<br>
> 类型：ADR<br>
> 日期：2026-08-27

## 背景

Component 的配置会和动态服务依赖共同决定一轮 Fiber 运行。配置更新、服务替换、异步启动和异步清理可能同时发生；如果它们分别驱动生命周期，就可能并发执行两轮组件、让新配置在旧运行清理期间提前可见，或在清理失败后继续启动新目标。

配置还允许通过 Standard Schema 提供默认值和转换结果，因此原始输入、已验证配置和运行实际使用的配置需要明确区分。

## 决策

### 同步校验与提交边界

- Component 可以通过 `Config` 提供 Standard Schema；Core 只支持同步校验，遇到异步校验结果时立即拒绝；
- 初次安装在组件入口执行前完成校验。校验失败时 Fiber 进入 `FAILED`，保留原始输入供显式 `restart()` 重新校验；
- `fiber.update(input)` 先校验和转换输入。校验失败不会提交新配置，也不会打断当前运行；
- 校验成功的结果经过 `internal/update` waterfall。监听器只有调用 `next()` 才会提交更新，因此可以包装、转换或取消提交；
- 一次提交原子地替换 `fiber.config`、递增配置版本并请求生命周期收敛。较旧的并发更新不得覆盖较新的请求；
- `fiber.restart()` 使用当前已验证配置重新建立运行；如果初次校验失败，则先用保留的原始输入重新校验。Root Fiber 的 `restart()` 只清空当前 Effect 树，Root Context 仍可复用；永久销毁的普通 Fiber 不可更新或重启。

### 一个运行目标与一条协调队列

- Fiber 的运行目标由服务依赖快照 epoch 和配置版本共同标识；两者任何一个变化都通过同一条串行协调队列处理；
- 每轮组件入口和其清理固定使用启动时的依赖快照与配置值。运行期间的新目标不能改变旧运行读取到的值；
- 目标变化时必须先完整卸载旧运行，再启动最新目标。异步入口或异步清理未结束时不得并发启动另一轮；
- 快速连续更新可以跳过尚未启动的中间版本，但每个已进入提交路径的 `update()` 都要等 Fiber 收敛到调用期间出现的最新请求；
- 缺少必需依赖时，已提交配置仍然成为当前目标配置，Fiber 保持 `PENDING`，待依赖满足后以最新配置启动。

### 失败与恢复

- 启动失败会缓存失败目标，避免在目标未变化时空转重试；配置或依赖目标变化后可以重新尝试；
- 旧运行清理失败时记录原错误并阻止新目标启动。Fiber 进入 `FAILED`，且不会因依赖通知自动重试；调用方必须显式 `restart()`、提交一次通过校验的 `update()`，或永久销毁 Fiber；
- 组件启动失败后的回滚如果也发生清理错误，同样进入上述阻塞状态；仅改变依赖 epoch 不得绕过它；
- 依赖变化和配置变化同时发生时只收敛到两者的最新组合，不允许清理期间切换快照。

## 后果

- 配置与动态服务共用一套启动、回滚和清理不变量，不需要两套竞争的生命周期状态机；
- `fiber.config` 表示最近一次已提交的验证结果，不一定表示当前存在活跃运行；清理失败时它可能已经指向尚未启动的新配置；
- Waterfall 扩展点可以延迟或取消提交，但异步监听器会相应延长 `update()`；
- Core 暂不支持异步 Standard Schema。若未来引入，必须另行决定校验取消、请求排序和销毁期间的结果处理。

## 考虑过的替代方案

### 配置更新直接重启组件

实现简单，但会绕过正在发生的服务切换和异步清理，无法保证只存在一轮运行。

### 配置与依赖分别维护队列

能够独立调度两类变化，但会产生顺序竞争，需要额外协议决定最终快照与配置的组合。

### 清理失败后自动重试或继续启动

可提高表面可用性，但旧资源的状态已经不确定，继续启动可能造成重复监听、资源泄漏或两轮运行并存。因此恢复必须由显式操作触发。

### 支持异步 Standard Schema

生态兼容性更强，但需要取消和过期结果处理。0.1 阶段先保持同步边界，避免校验任务成为第二条并发状态机。
