# ADR-0012：依赖诊断与开发辅助的生命周期边界

> 状态：Proposed<br>
> 类型：ADR<br>
> 日期：2026-09-05

## 背景

组件停留在 PENDING 时，单一状态不足以解释服务缺失、提供者正在初始化或 Service.check 不通过。开发者还需要可撤销的定时器，以及修改代码后可以确认旧资源已经退出的重启流程。这些辅助能力不应改变既有依赖解析、清理协议或嵌入宿主的权利。

## 决策

Core 在 Fiber 只读诊断中提供依赖解析的观察结果。缺少实现和提供者状态来自同一隔离地址的元数据；Service.check 的结果只记录真实依赖捕获时发生的调用。诊断不会为了得出更完整的结论再次运行用户检查，未执行的检查明确标为 unchecked。Loader 在 Entry 快照中投影同一诊断，保留父 Entry 阻塞与服务依赖阻塞的区别。

已安装的 Service 子类可以用静态 provide 字段声明已知提供者。声明不是服务实现，不参与依赖满足判定；普通组件在第一次 provide 之前没有可推断的服务清单。声明与安装生命周期一同释放，不保留已销毁 Fiber 的历史强引用。对外只输出冻结身份和状态数据。

Timer 是独立服务包，通过 Service 调用方 Context 的 Effect 登记原生 timeout 和 interval。一次性定时器触发时自动撤销登记；取消只停止未来调度，不等待已经开始的回调。异步业务如需完整等待，应由组件自己的资源 Effect 管理，避免回调销毁自身时产生自等待。回调同步或异步失败进入日志，并停止该定时器；这不改变所属 Fiber 的生命周期结果。当前不增加 mixin 或 Promise 延时接口。

开发重启在示例宿主中实现。每轮先等待旧应用退出，再构建并启动新进程；构建失败保持停止。开发宿主合并连续修改，任何时刻最多一轮构建和一个应用进程。IPC 提供跨平台的优雅退出请求，最终仍执行现有应用 close；清理超时后的强制结束属于宿主策略。源码修改不通过 Core 或 Loader 模块缓存模拟 HMR。

## 后果

- 依赖诊断可以解释真实已观察到的阻塞，但不会执行用户代码来猜测未来结果。
- Timer 使用者不需要手写 clearTimeout/clearInterval，仍需明确管理回调自己的异步资源。
- 开发重启会有停机间隔；这使构建结果、模块身份和资源清理顺序可以直接验证。
- 诊断、Timer 包消费者和开发父子进程都需要回归覆盖；包的独立安装验证包含 Timer 和开发脚本。

## 考虑过的替代方案

在 inspect 时重新执行 Service.check 会让观察改变用户代码调用次数；扫描任意组件函数来猜测服务名则没有可靠语义。两者均不采用。

把 Timer 放入 Core 或预先引入 mixin 会扩大本轮公共接口。直接使用 Node watch 重启目标进程无法保证跨平台都经过应用的资源清理流程，因此开发宿主显式等待关闭。
