# ADR-0003：服务身份由名称与隔离标签共同确定

> 状态：Accepted<br>
> 类型：ADR<br>
> 日期：2026-08-27

## 背景

Nya 最初以服务名作为一棵 Root Context 内的唯一服务身份。这个模型足以表达单一默认实现，但无法让生产实现、测试实现或不同组件分支同时提供同名能力。单纯在 Context 上覆盖属性也不能满足动态依赖要求，因为 `provide()`、读取、依赖快照、反向订阅和变化通知必须指向同一个服务位置。

隔离还必须维持现有生命周期不变量：Fiber 一轮运行只能使用启动时捕获的固定依赖快照，旧运行清理期间不能切换到另一个服务实现。

## 决策

- 一项服务在运行时中的地址由 Root Context、非空服务名和 `IsolationLabel` 共同确定；公开的 `IsolationLabel` 是 `symbol` 的类型别名。
- 每棵 Root Context 为每个未隔离服务名维护一个内部、稳定的默认标签。默认标签不作为公共 API 暴露。
- `context.isolate(name, label?)` 返回派生 Context，不修改原 Context。未传标签时创建新的唯一 Symbol；传入同一个显式标签时，同一 Root 内的不同 Context 分支共享对应服务地址。
- Context 的隔离映射按原型链继承。子 Context 只覆盖指定服务名的标签，其他服务继续沿 Context 原型链解析。
- 隔离采用严格匹配。当前地址没有有效实现时，消费者保持 `PENDING`；运行时不得回退到该服务名的默认地址。
- `provide()`、`get()`、Context 属性读取、`has()`、依赖捕获、订阅和变化通知必须通过同一地址解析规则定位 slot。同一地址最多有一个实现，不同标签可以同时提供同名服务。
- 依赖快照继续以服务名索引实现，并以实现 id 组成 epoch。地址只决定捕获和通知范围；Fiber 一轮运行及其清理始终读取已经捕获的旧快照。
- 同一个 Symbol 在不同 Root Context 中不共享服务，因为 Root 本身也是服务身份的一部分。
- `isolate()` 只派生服务解析视图，不创建 Fiber，也没有独立销毁语义。资源仍由实际执行 `provide()`、安装组件或创建 Effect 的 Fiber 所有。
- 本决策只把服务寻址与依赖通知纳入 Current。Service 作为事件 `thisArg` 时的隔离过滤仍依赖后续调用方 Context 追踪，不在本次实现范围内。

## 后果

- 默认 Context 的服务行为保持不变，而测试或局部分支可以与默认实现同时提供同名能力。
- 显式共享 Symbol 能表达跨分支共享；省略标签则安全地得到互不相同的局部地址。
- 严格不回退使缺失依赖可以被 Fiber 状态直接观察，避免局部实现暂时消失时意外使用默认服务。
- ServiceRegistry 需要按服务名和标签维护二维 slot，并在服务实现中保留地址与提供方 Context。
- 隔离 Context 不是权限、进程或安全沙箱；组件仍能访问同一 JavaScript 进程中的文件系统、网络、环境变量和全局对象。
- Intercept、调用方绑定 Service facade、callable Service、mixin 以及与隔离标签一致的事件过滤需要后续 ADR 或实现继续定义。

## 考虑过的替代方案

### 缺失隔离实现时回退默认服务

回退能减少 `PENDING`，但会让消费者在局部实现消失时静默切换能力，破坏明确作用域和固定快照的心智模型，因此不采用。

### 使用字符串作为公开标签

字符串便于配置文件表达，但容易发生跨模块命名碰撞。Core 只接受 Symbol；未来 Loader 可以负责把稳定字符串配置映射为 Symbol。

### 每个隔离 Context 创建独立 ServiceRegistry

独立注册表会复制订阅和通知基础设施，也难以表达多个分支共享同一显式标签。保留 Root 级注册表并使用二维地址能用一个一致模型覆盖默认、独立和共享三种情况。
