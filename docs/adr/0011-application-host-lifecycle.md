# ADR-0011：应用组合与宿主进程生命周期

> 状态：Proposed<br>
> 类型：ADR<br>
> 日期：2026-09-05

## 背景

Core 和 Loader 已能管理组件、依赖与资源清理，但独立程序仍需决定如何读取配置、等待启动、接收退出信号和处理超时。若把这些职责直接写进组件，组件就会依赖进程全局状态，嵌入其他程序或测试时也可能意外退出宿主。

任务日志示例需要同时演示两种用法：作为 Node.js 命令行程序持续写入 JSONL 文件，以及作为现有程序内的一棵 Nya 运行时树被启动、更新和关闭。它还需要在不依赖仓库 workspace 链接的目录中安装和运行，证明消费者能只使用公开包入口。

## 决策

### 应用组合层只管理自己的运行时

`createApplication(config)` 创建独立 Context，并返回 `context`、`start()`、`updateJob()`、`setEnabled()`、`failure` 和 `close()`。应用通过 Core、Loader 和控制台 Logger 的公开 API 组合存储与任务组件；组件入口只负责本次运行的资源与清理，不解析命令行、不安装进程信号处理器，也不调用 `process.exit()`。

存储组件提供追加任务记录的服务，任务组件声明这项依赖。禁用存储会让任务停止当前运行并等待依赖恢复；重新启用后按新的服务实现建立运行。任务配置更新和任务启停通过 Loader Entry 进行，避免另建组件状态机。

`failure` 是应用运行期间首个失败的单次通知：以错误值 resolve，供宿主与其他结束条件竞速。它不因正常关闭而伪造错误，也不替代具体操作自身的拒绝结果。`close()` 缓存并返回同一个 Promise，重复或并发调用等待同一轮资源清理；清理错误仍向等待者报告。

### 宿主负责配置、信号、超时与退出

Node 宿主读取并校验 JSON 配置，向应用传入解析后的值。配置覆盖存储文件、任务间隔与标签、日志级别、启动和关闭等待时间。相对存储路径以配置文件所在目录为基准；未指定 `--config` 时读取工作目录中的 `config.json`。缺少文件属于配置错误，存在的空对象配置才应用默认值：存储文件为 `./data/tasks.jsonl`，任务间隔为 1000 毫秒、标签为 `heartbeat`，日志级别为 `info`，启动和关闭等待时间各为 10000 毫秒。

宿主等待应用启动，并将运行失败、演示完成和 SIGINT / SIGTERM 统一汇入关闭路径。关闭路径同时等待应用清理与已启动的演示收尾，共用一次关闭期限，保留两者各自的错误；重复信号不会重置期限。信号监听器和等待用定时器也由宿主负责撤销。应用层不安装这些进程级资源，嵌入者可以采用自己的服务器、窗口或测试框架生命周期。

启动或关闭等待到期表示宿主不再继续等待，不表示 Core 已取消组件代码。关闭超时后，命令行宿主通过自己的 `forceExit` 边界终止进程；Core 仍不提供强制取消 cleanup 的语义，也不能保证超时退出时所有文件写入都已完成。

退出码由宿主决定：演示和帮助正常完成为 0，配置错误为 2，运行失败、清理失败或超时为 1。收到 SIGINT 或 SIGTERM 且清理成功时分别为 130 和 143；失败和超时优先于信号的成功退出码。

### 用独立目录验证消费者边界

仓库的 `example:pack` 构建发布包并生成 `artifacts/task-journal/`。目录包含示例源码、构建输出、配置、README、package.json、tsconfig.json 和 `vendor/*.tgz`；本地 Nya 依赖通过归档文件安装，不依赖仓库内包的源码路径、私有字段或 workspace 符号链接。

独立验证按 `npm install`、`npm run build`、`npm run demo` 的顺序执行；持续运行使用 `npm start -- --config ./config.json`。这只是可搬移的示例交付目录，不意味着 npm registry 已发布这些版本，也不意味着安装过程完全离线。

演示程序根据已写入记录的事件推进，依次覆盖任务配置更新、禁用与恢复任务、禁用与恢复存储。它不以固定 sleep 时长断言任务已执行，用事件和运行时状态验证每一步确实完成。

## 后果

- 同一套组件可以进入命令行程序、测试或其他宿主，进程策略留在最外层。
- 宿主必须明确等待 `failure` 并调用 `close()`；只等待启动完成无法发现之后的运行失败。
- 故障后的退出仍尝试等待资源清理，但关闭超时可能导致未完成的工作被进程退出打断。
- 示例需要同时验证组件行为、宿主信号与超时、真实文件输出和脱离 workspace 的安装路径。
- 默认值与 CLI 参数的当前事实保留在源码、配置样例和测试中，教程通过完整运行步骤解释这些边界。

## 考虑过的替代方案

在 Core 内统一读取配置、监听进程信号和设置 cleanup 超时，会把运行时绑定到 Node 进程，并给嵌入者强加退出策略。让组件直接调用 `process.exit()` 会跳过其他组件或宿主的清理，因此不采用。

只在 Playground 中执行示例无法验证归档包的导出和独立安装。复制整个 monorepo 虽然可以运行，但会掩盖 workspace 链接或仓库私有路径依赖，因此采用独立目录和本地归档依赖。
