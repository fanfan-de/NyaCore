# ADR-0001：文档采用仓库内可验证的 Docs-as-Code 模式

> 状态：Accepted<br>
> 类型：ADR<br>
> 日期：2026-08-25

## 背景

Nya 处于核心语义快速演进阶段。项目需要同时表达当前已经实现的行为和未来目标设计，而 AI 辅助开发会显著提高内容生成速度，也会增加产生重复、过期或缺少事实来源的文档的风险。

当前文档与源码位于同一仓库，但缺少统一入口、权威层级、贡献约定和自动检查。

## 决策

Nya 采用轻量 Docs-as-Code 模式：

- Markdown 文档与源码保存在同一仓库，并在同一个 Pull Request 中评审；
- 使用状态和文档类型区分当前行为、目标规范与历史决策；
- 以源码、类型和测试支撑当前行为，以 Accepted 规范和 ADR 记录设计约束；
- 使用 `AGENTS.md` 提供仓库地图和操作规则，不复制完整知识正文；
- 使用零依赖 CI 检查文档基本结构、本地链接和代码围栏；
- API 和配置参考在条件成熟时从代码、类型或 Schema 生成。

## 后果

- 文档变更可以和代码一样被审查、追踪和回滚；
- 贡献者和 AI 可以明确区分“现在如此”与“计划如此”；
- 当前不引入独立文档站点、数据库或向量检索服务，维护成本较低；
- 作者仍需对事实正确性负责，自动检查不能证明语义正确；
- 当外部用户和版本化需求增长时，需要另行决定发布站点和生成式 API Reference 工具。

## 考虑过的替代方案

### 独立 Wiki

编辑方便，但容易与代码评审和版本历史分离，不适合作为当前阶段的主要事实源。

### 立即引入完整文档平台

能够提供导航、搜索和部署，但现有文档规模尚小，新增依赖和配置的收益有限。

### 由 AI 自动生成全部文档

生成成本低，但无法单独保证事实来源、版本对应关系和架构决策的责任归属。
