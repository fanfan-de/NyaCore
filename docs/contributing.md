# 文档贡献指南

> 状态：Current<br>
> 类型：How-to<br>
> 适用范围：仓库内全部 Markdown 文档

## 1. 先确定文档影响

代码变更出现以下任一情况时，应更新文档：

- 增加、删除或修改公共 API；
- 改变可观察行为、错误或生命周期顺序；
- 增加配置、命令或运行前提；
- 接受新的跨模块设计约束；
- 现有示例不再能够运行。

纯内部重构不要求机械修改文档，但 Pull Request 应说明为什么没有文档影响。

## 2. 选择唯一的主要用途

- 教用户完整学习过程：Tutorial；
- 帮用户完成具体任务：How-to；
- 精确罗列 API 或配置：Reference；
- 解释概念和设计原因：Explanation；
- 定义目标语义和约束：Specification；
- 记录一次不可忽略的设计选择：ADR。

一篇文档可以链接到其他类型，但不要同时承担所有职责。

## 3. 写入正确的位置

当前仓库规模较小，已有文件保持稳定路径。新增多个同类文档时再创建对应目录：

```text
docs/
  tutorials/
  how-to/
  reference/
  explanation/
  spec/
  adr/
```

文件名使用简短、稳定的英文 kebab-case；标题和正文可以使用中文。移动已有文件时必须同步更新仓库内链接。

## 4. 标明状态和范围

长期维护的文档应在一级标题后标明状态、类型和适用范围。规范与 ADR 必须区分 Proposed 和 Accepted。描述当前行为的文档只能在有源码或测试证据时标为 Current。

## 5. 让示例可验证

优先级依次为：

1. 示例直接来自测试或 playground；
2. 示例代码在 CI 中编译；
3. 无法自动执行的伪代码明确标记为伪代码，并说明省略内容。

不要手写复制能够从 TypeScript 类型、Schema、CLI 帮助或其他机器可读事实生成的完整参考表。

## 6. 本地检查

只修改文档时运行：

```bash
npm run docs:check
```

代码和文档同时修改时运行：

```bash
npm run check
```

`docs:check` 检查 Markdown 是否恰好有一个一级标题、代码围栏是否闭合，以及相对链接的目标是否存在。外部链接的可用性不作为每次提交的阻塞条件。

## 7. 使用 AI 的边界

AI 可以帮助生成初稿、整理结构、发现代码与文档之间的差异，但不能凭自己的输出证明某个事实。合并前，作者需要把关键陈述核对到源码、测试、Accepted 规范、ADR 或外部一手资料。
